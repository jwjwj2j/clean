# 无障碍服务存活守护（ColorOS 17 等系统的"自动关闭"应对）

> 目标：在**不使用 ADB / Shizuku / root、不上架商店**的前提下，尽可能延长无障碍服务的存活时间，
> 并在被系统关闭后尽快恢复可用。
>
> 结论先放最前面：**"自动重新开启"做不到；"尽快发现 + 一键恢复 + 进程自愈"做得到。**
> 下面把能做到的、做不到的、以及为什么，逐条说清楚。

---

## 0. 平台硬约束（必须先接受这一条）

系统里那个无障碍开关存放在 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES`，
写入它的前提是持有 `WRITE_SECURE_SETTINGS`。该权限的保护级别是
`signature|privileged|development`：只有系统签名应用、预置应用，或者通过
ADB / root / Shizuku 用特权身份写入才能获得。

侧载的普通应用**拿不到它**，因此：

- 应用**无法**用任何代码把系统开关重新打开；
- 应用**无法**阻止 ColorOS 关闭它；
- 任何声称"纯代码自动重开无障碍"的方案，在没有特权的设备上要么无效，要么是靠别的手段
  （root / Shizuku / 无障碍快捷方式诱导点击 / 1 像素 Activity 等），而你已经排除了前两类。

所以本方案的设计目标被重新定义为两件事：

1. **缩短"服务已死"到"用户知道"的时延**（越短越好，目标秒级）；
2. **把恢复动作压缩到一次点击**（通知 → 系统开关页 → 打开 → 自动复核），
   同时**提高进程存活概率**，让第 1 条在进程被杀时仍然成立。

## 1. 进程保活的具体实现

| 方案 | 是否落地 | 预期效果 | 局限 |
| --- | --- | --- | --- |
| **常驻前台服务**（`StatusService`，`specialUse` 类型 + `START_STICKY`） | ✅ 已实现（原有 + 本次增强） | 常规情况下可长期存活；被杀后系统会尝试重建 | 厂商可无条件强杀；需要通知权限与 `FOREGROUND_SERVICE_SPECIAL_USE` |
| **无障碍叠加层保活**（`TYPE_ACCESSIBILITY_OVERLAY`，原有 `KeepAliveOverlayCoordinator`） | ✅ 原有 | 提升进程优先级 | **无障碍一死叠加层就跟着没了** —— 它救不了"无障碍被关"这个场景，只能防"进程被内存压力回收" |
| **JobScheduler 持久化周期任务**（15 分钟） | ✅ 新增 | **进程被杀之后仍能把应用拉起来自检** —— 这是唯一一条"死后复活"的路径 | 受 Doze 与厂商调度影响，可能被推迟到几十分钟到数小时；`setPersisted(true)` 需要开机广播权限 |
| **AlarmManager 闹钟**（优先精确，无权限则 `setAndAllowWhileIdle`） | ✅ 新增 | 补上 Job 被推迟的窗口 | 没有 `SCHEDULE_EXACT_ALARM`（Android 12+ 特殊权限，侧载默认不授予）时为不精确闹钟；Doze 下最早 15 分钟一次 |
| **开机 / 覆盖安装 / 解锁广播**（`A11yBootReceiver`） | ✅ 新增 | 重启后立刻重建守护并自检 | ColorOS 默认可能禁止侧载应用自启动，需要用户手动允许 |
| **双进程守护**（`:guard` 进程互拉） | ❌ **有意不做** | 理论上两个进程互相 `bindService` 互拉 | Android 8+ 禁止后台启动服务；同应用的多进程通常被**一起**清理；更关键的是它属于典型的恶意保活手法，容易被系统判定为"重点关照对象"，**净效果可能是负的**。若确实要做，见 §5 的可选实现 |
| **WorkManager** | ❌ 未采用 | 与 `JobScheduler` 能力等价 | 会新增一个 androidx 依赖；本项目至今保持零新增依赖，用系统 API 即可 |
| **1 像素 Activity / 静音音频 / 前台播放** | ❌ 不采用 | 能短暂提升优先级 | 明确的恶意保活手法，违反系统设计意图，也与本产品"给普通人用的干净工具"定位冲突 |

**小结**：保活能提高存活概率，但**没有任何非特权手段能保证活着**。真正决定存活时长的是
厂商的后台策略与应用是否在白名单里 —— 这部分只能引导用户在系统设置里完成（见 §4 的引导清单）。

## 2. 无障碍被关闭后的检测与"重新拉起"

### 2.1 "重新拉起"的准确含义

- 能拉起的：**我们自己的进程、前台服务、守护任务**；
- 不能拉起的：**系统里那个无障碍开关** —— 它只能由用户点。

因此实现是「检测 → 通知/全屏提醒 → 一键跳到开关页 → 用户打开 → 自动复核」。

### 2.2 四条互相兜底的检测路径

| 路径 | 触发时机 | 典型时延 | 失效条件 |
| --- | --- | --- | --- |
| `A11yService.onDestroy` / `onUnbind` | 服务被系统关闭的那一瞬间 | **1–3 秒** | 进程被一起杀掉时不执行 |
| `StatusService` 内的 10 分钟轮询 | 进程还活着时 | ≤ 10 分钟 | 进程已死 |
| `JobScheduler` 周期任务（15 分钟） | 进程被杀之后 | 15 分钟 ~ 数小时 | 被厂商冻结/推迟 |
| `AlarmManager` 闹钟 + 开机广播 | Doze / 重启 | 类似上一条 | 同上 |

检测本身用两条独立的路交叉验证，避免单一来源在个别 ROM 上读不到：

1. `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES`（同步快照读）；
2. `AccessibilityManager.getEnabledAccessibilityServiceList()`（公开 API 兜底）。

### 2.3 恢复动作（尽可能短）

1. 被判定为"系统关闭"时，发一条 **`IMPORTANCE_HIGH`** 的通知（新渠道 `Guard`）；
   息屏时若有全屏 Intent 权限（`USE_FULL_SCREEN_INTENT`）则直接弹全屏提醒，无权限自动降级为高优先级横幅；
2. 点通知进入 `A11yRecoveryActivity`（**无界面**，透明主题）：它直接跳到本应用无障碍服务的
   系统详情页，按「扁平化 ComponentName 字符串 → ComponentName 对象 → 无障碍列表页」三级降级，
   保证任何 ROM 上都能到达开关附近；
3. 用户打开开关返回 → 页面自动复核 → 清掉通知 + 提示"已恢复"。

> `Settings.ACTION_ACCESSIBILITY_DETAILS_SETTINGS` 在当前编译平台的 `android.jar`（android-37.0）里
> **没有对应常量**，所以代码里用动作串字面量 `android.settings.ACCESSIBILITY_DETAILS_SETTINGS`。

### 2.4 误报抑制（很重要，否则用户会被烦到卸载）

用「用户意图 + 事故编号」两个概念把噪音压到最低：

- **用户意图**：只有服务真正连接过（`onServiceConnected`）才认为"用户想用它"；
- **主动关闭标记**：应用内开关与磁贴走的是 `disableSelf()`（不经过 `shutdown()`），
  所以在关闭前先 `markIntentionalStop()`；加上 `shutdown()` 与"已切到自动化模式"两处，
  三种主动关闭都**不会**触发恢复提醒；
- **事故编号**：用"最后一次确认活着的时刻"作为编号，**同一次死亡只提醒一次**，
  服务重新连上后编号刷新，才会再次提醒。

## 3. ColorOS 17「潮汐引擎」的应对思路

**先说清楚：我没有 ColorOS 17 内部实现的公开资料，"潮汐引擎"是 OPPO 的后台调度品牌名，
没有面向第三方应用的公开 API、白名单接口或绕过方式。** 因此下面的应对全部建立在
"把它当成一个会随时清理我、并且我看不见它"的黑盒来设计，而不是"想办法绕过它"。

从可观测现象反推（以下为**推断**，未在真机逐项验证）：

| 现象 | 可能的机制 | 能做的应对 |
| --- | --- | --- |
| 侧载应用被优先清理 | 不在应用商店信誉库 / 不在厂商白名单 | 引导用户手动加入电池与自启动白名单（§4）；`isAccessibilityTool=true`（本项目已开启，系统对"无障碍工具"的判定更宽松） |
| 无障碍开关被系统重置 | 长时间后台 + 省电策略下的权限回收 | 无法阻止，只能缩短"发现→恢复"的时延（§2） |
| 应用被"速冻"后完全不动 | 应用速冻 / 智能省电冻结后台 | 引导用户在电池设置里选"允许后台活动"、关闭对该应用的智能省电 |
| 重启后守护消失 | 自启动默认被拦 | 引导开启自启动/关联启动；同时保留开机广播这条路径 |

**结论**：面对厂商调度，唯一稳的策略是"假设它随时会杀" —— 把不可控的存活问题，转化成
可控的**检测时延**与**恢复成本**问题。这也是本方案的全部设计取向。

## 4. 用户可以自己完成的系统侧设置（不需要 ADB）

这些不是"绕过"，而是系统本来就提供的白名单入口。建议做成首次引导 + 保活向导页逐项深链：

1. 设置 → 电池 → 应用耗电管理 → CLEAN：**允许后台活动 / 不优化**
   （应用内已有"忽略电池优化"的申请入口，走 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`）；
2. 设置 → 应用管理 → CLEAN → **允许自启动 / 允许关联启动**；
3. 多任务界面**锁定** CLEAN 的卡片；
4. 若系统有"应用速冻"：把 CLEAN 加入**不速冻**名单；
5. 关闭针对 CLEAN 的"智能省电 / 深度睡眠"。

> 关于开发者选项里的"禁止权限监控"：确实能减少系统回收权限类操作，但对普通用户门槛太高，
> 按你的要求不纳入方案，只作为"给懂的人"的可选建议。

## 5. 预期效果与局限（诚实版）

### 能达成的

- 无障碍被系统关闭后，**同进程情况下 1–3 秒内**发出高优先级提醒；
- 进程也被杀时，**最快 15 分钟**（Job/闹钟被正常调度）发现并提醒；被厂商推迟时会显著变长；
- 恢复动作从"用户自己去找设置"压缩到"**点通知 → 打开开关**"；
- 重启手机、覆盖安装后守护自动重建；
- **不会**因为用户自己关开关而误报。

### 明确达不成的

- **不能阻止系统再次关闭它**（预期仍是"每 7–8 小时被关一次"，只是用户会被及时提醒）；
- **不能自动重新开启**（无 `WRITE_SECURE_SETTINGS`）；
- **不能保证进程不被清理**，也不能保证 Job/闹钟被准时调度；
- 用户长期不理这条通知（不点、不关），则拦截会一直处于失效状态 —— 这是**提醒机制**而非**修复机制**。

### 如果要"彻底解决"

按可靠性排序（都已超出你给定的约束）：

| 手段 | 效果 | 代价 |
| --- | --- | --- |
| ADB 执行一次 `settings put secure enabled_accessibility_services ...`（或 `pm grant` 后用代码自愈） | 可做到接近自动恢复 | 需要一次 ADB，你已排除 |
| Shizuku | 可做到自动恢复 | 你已排除 |
| root / 系统签名 / 预置应用 | 彻底解决 | 你已排除 |
| 上架 OPPO 商店 | 进入正规应用白名单，后台策略宽松很多 | 你已排除 |

## 7. 验收 / 自测步骤

1. 装上后开启无障碍 → 状态通知恢复正常文案，无恢复提醒；
2. **在系统设置里手动关掉** CLEAN 的无障碍 → 数秒内应出现"无障碍服务已被系统关闭"高优先级通知；
3. 点该通知 → 应直接跳到 CLEAN 的无障碍开关页（若 ROM 忽略深链，则落在无障碍列表页）；
   打开开关返回 → 应提示"已恢复"，通知消失；
4. **在应用内关掉总开关** → **不应**出现恢复提醒（验证主动关闭标记）；
5. 重启手机 → 守护自动重建；无障碍若已开则无提醒，若已关则出现提醒；
6. 有 ADB 的话可强制触发周期任务验证：
   `adb shell cmd jobscheduler run -f <包名> 1001`。
